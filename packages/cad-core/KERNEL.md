### Isolated prototype scope

- `curves.ts`: analytic ellipse/circle point, derivative, tangent and curvature, normalized arc evaluation, and circle projection with axis ambiguity. No general ellipse projection, curve intersections, exact arc bounds or broad precision analysis. Invalid inputs can throw, rather than all using structured diagnostics.
- `surfaces.ts`: analytic finite axial revolved-line surface (cylinder or truncated cone), derivatives and normal; finite-cylinder projection only. It rejects the axis/apex. No sphere, torus, general profile of revolution, general surface intersection/projection/bounds or singularity treatment.
- `revolve-*.ts`: independent curved topology, **not** a widening of the planar validator. One solved XY line rectangle strictly to the right of an in-plane global +Y axis; full or signed partial sweep (not arbitrary axes/frames, curves, concave profiles, axis contact or multiple loops). The builder returns the solved sketch copy. Full sweeps contain actual circle curves, cylindrical/planar faces, pcurves, annular cap inner loops and same-face periodic seam coedges. Partial sweeps add planar radial cuts. IDs derive from operation/source roles. Tests cover seam pairing, signed sweeps and a few topology mutations. There is no generic imported curved B-rep support, singularity handling or general self-intersection proof.
- `checkRevolution` samples pcurves against edge/surface geometry, checks the narrow topology and parameter/frame consistency, and `assessRevolution` labels its scope `rectangular-revolution-only`. A scoped `valid` result is **not** a general 3D validity certificate. `incomplete`, `unsupported` and `invalid` are implemented; `numerically-uncertain` is declared but the assessment function does not yet classify cases into it. Operation-level structured uncertainty diagnostics exist for several unsupported cases, not all possible numerical failures.
- `revolutionProperties` uses analytical annular-sector formulas and B-rep-associated parameters after the narrow validation; it does not derive its integrals directly from arbitrary face trims, and validation samples do not certify arbitrary hostile B-reps. Surface/edge areas, volume, centroid and bounds do not use triangles. Reported tolerances are implementation policy, **not a certified error bound**. There is no general numerical integration or material property interface.
- `tessellateRevolution` samples a shared angular grid for all faces with linear/angular limits, face/edge mapping and caps for segments/triangles; selected full/partial signed cases are checked for paired mesh edges. It rejects limits instead of silently reducing quality and checks a synchronous cancellation callback. It is not a general adaptive surface tessellator, has no worker isolation/progress, and a synchronous callback cannot observe events queued on the same blocked thread. Floating-point deflection is not independently certified.
- `revolve-provenance.ts` resolves only exact IDs and matching ancestry; missing or multiple candidates do not get guessed. Complete split/merge/deletion/topological naming remains unsolved.
- `boolean-box.ts` operates on exact axis-aligned box B-reps, constructs new planar boxes via actual coordinates (not meshes), checks them, maps output faces conservatively to input face IDs and retains both input solid IDs. The existing planar provenance type gained an additive Boolean operation variant; prior extrusion values and document contracts are unchanged. Result sets are cloned so unchanged output does not alias inputs. Unchanged solids keep their original entity provenance; the result wrapper carries the Boolean operation. Boolean history is not complete topological naming, and planar validation is not hardened for hostile imports.

### Box Boolean support matrix (volume solids only)

| Relation/case | Union | Intersection | Subtraction A − B | Split A by B |
| --- | --- | --- | --- | --- |
| Strictly disjoint | two unchanged boxes | empty | A | A |
| Exactly coincident or B contains A | containing box | overlap box | empty | A |
| A contains B | A | B-shaped overlap box | only when overlap spans A in two axes; otherwise unsupported cavity/non-box | same cross-section restriction |
| Positive overlap | only if union is one box (same extents in two axes) | overlap box | only when overlap spans A in two axes; one or two box components | same restriction; includes intersection component |
| Exact face contact | one box only if cross-sections match | empty volume | A | A |
| Exact edge/point contact | unsupported | empty volume | A | A |
| Near-coincident distinct boundaries within tolerance | numerically uncertain | numerically uncertain | numerically uncertain | numerically uncertain |

Inputs must be supported exactly axis-aligned planar boxes; slanted/rotated boxes, non-box results, overlapping L-shapes, cavities, curved solids and all curved Boolean pairs are unsupported. Empty intersection on contact means no **3D volume** is returned, not that lower-dimensional contact does not exist. Split results are separate solids and may share interfaces. No input is intentionally modified on success or failure; these are experimental algorithms, not general-purpose Boolean or robustness guarantees.

## Part 1 audit and integration boundary

`math.ts` provides finite-number checks, bounded coordinates (±1,000,000 m), `Vec2`/`Vec3`, vector operations and row-major transformations. It uses metres and binary64. `sketch.ts` supplies versioned XY sketch entities/constraints and string IDs; the only existing sketch frame is global XY, not an arbitrary stored 3D coordinate system. `solver.ts` must be treated as experimental: its Jacobian/DOF diagnostics and nonlinear solution have the limits in `docs/cad-native/01-foundation.md`. `document.ts` is a wire contract, not a source for automatic retrieval. The opt-in server API and migration 026 are not touched by this phase; migration 026 is automatically applied on application boot and its down migration destroys CAD data, so no rollback is assumed lossless. The disabled API remains disabled by default.

Extrusion accepts a `Sketch` value supplied by its caller, validates it and calls the existing solver on a copy; it returns the actual solved sketch along with the result so that movement caused by constraint solving is visible to the caller. It never writes back to the input or to storage. It consumes non-construction lines only and rejects other non-construction entity kinds. This is a testable adapter, not an integrated document/feature-history pipeline. The development API is available via the local `src/kernel/index.ts` module rather than being wired into the app's package entry point.

## Implemented subset and algorithms

- `src/kernel/types.ts`: separate straight-line geometry and plane surfaces from topology: vertices, segment edges, oriented coedges, ordered loops, faces and a single closed shell. Vertex/edge incidence, coedge links, face adjacency and source provenance are represented explicitly. There is no triangle mesh in the B-rep.
- `geometry.ts` reuses existing vectors and provides the global XY frame, frame-point evaluation, orthonormal/right-handed frame validation, segment evaluation and plane projection. The extrusion path supports **XY and ±Z only**; arbitrary frames, axes and most requested 3D analytic primitives are not implemented.
- `extrude.ts` accepts one simple closed loop of 3–16 lines. It assembles unordered/reversed endpoints within tolerance, rejects branches, gaps, collinear adjacent edges, crossings/touching and unsupported curves/loops, orients the polygon CCW and builds actual shared line edges and planar faces. Endpoint gaps within tolerance are replaced by their midpoint in the generated B-rep only. Blind positive/negative and symmetric depth are supported. The source and any previous solid remain unchanged on failure. The existing solver's resource/conditioning limits still apply.
- `topology.ts` checks IDs, endpoint/curve agreement, vertex incidence, coedge cycles, two oppositely oriented uses per edge, planarity and loop orientation, adjacency, shell connectedness and Euler characteristic for this narrow planar, single-shell, genus-zero subset. Properties use signed boundary integrals for volume and centroid and oriented planar polygon area for faces; bounds and edge lengths come from B-rep geometry, **not** the display mesh.
- `tessellation.ts` triangulates supported planar loops via ear clipping, records source face ID on each triangle and topological edge ID on each displayed edge, and rejects uncertain ears. Planar geometry has exact straight edges, so deflection/quality settings do not apply. Curved-face tessellation is absent.
- `provenance.ts` attaches operation ID, source sketch/revision, source entity IDs and semantic role to generated vertices/edges/faces/shell/solid. Deterministic IDs use caller-supplied operation identity and source identifiers. Face reference resolution requires exact ID and matching ancestry; ambiguous candidates remain unresolved. This is not a complete modification/split/merge history, and does not guarantee stable naming through topology changes. The caller must ensure operation IDs are unique and persist feature identity.

## Numeric policy and validation limits

All geometry uses IEEE-754 binary64, not exact predicates. Model tolerance records `scaleMetres` (largest bounding span), max coordinate magnitude, `lengthMetres = max(1e-10, scale*1e-9, maxCoordinate*Number.EPSILON*32)`, `areaMetres2 = lengthMetres*max(scale,lengthMetres)`, and a 1e-10 radian angular threshold. Segment crossings use local orientation determinants and length-scaled uncertainty; near-zero cases are rejected rather than declared safe. Vertices are checked against the recorded context, recomputed from the generated model. These thresholds are conservative implementation choices, not certified engineering tolerances; extreme scales/aspect ratios are unsupported or may be rejected. Coordinates and generated points must fit the existing ±1e6 m limit.

`checkTopology` is a **limited combinatorial/planar check**, not a proof that an arbitrary mutated or imported shell is embedded, non-self-intersecting, or a valid solid. Generated extrusion additionally checks its source profile before construction; there is no general 3D face/face intersection validation. Do not accept arbitrary untrusted serialized B-reps or treat this check as production-grade integrity verification. Provenance and tolerance metadata themselves are not hardened for hostile input. Further numerical review, fuzzing and independent topology/geometry validation are required.

This is an uncontrolled single-process microbenchmark, not a performance guarantee or a maximum-size benchmark.
