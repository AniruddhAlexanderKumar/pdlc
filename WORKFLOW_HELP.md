# Workflow and Help Centre implementation

## Workflow audit and changes

The available workspace roles are owner, admin and member; global system administrators are separate, and temporary demo guests have additional restrictions. The application does not currently model students, teachers, institutional administrators, project-specific roles or educational cohorts. It stores products and product tasks separately from projects and issues. Requirements, design decisions, verification evidence and releases are not first-class records. The guides must not imply otherwise.

The dashboard now offers role-aware starting actions and an assigned-work card. Navigation retains existing destinations, with less frequent tools grouped in the expanded sidebar. The quick-actions dialog supports keyboard opening with Ctrl/Command+K, searches existing projects and products, and hides actions the current workspace role cannot use. Project creation suggests an editable unique key and opens the issue list directly; issue cards now support reassignment through the existing workspace-scoped update API. The optional first-project guide highlights the project form and issue action, and records user-marked steps, skip and completion per user/workspace; it does not automatically verify that a step occurred. Demo walkthrough progress remains local. Existing authorization, status changes, review controls and audit mechanisms are not replaced.

## Help content and support

Migration 018 installs the initial plain-text guides, article revisions, user/workspace progress and support tickets. Published content is visible according to its audience (`everyone` or workspace owners/admins); drafts and archives are visible only to global system administrators. System admins can create, edit, publish or archive articles, set categories/keywords/audience and inspect revision snapshots. Migration 019 corrects only the exact unchanged original project-issues guide and adds a revision; admin-edited text is not overwritten. New/updated guides must be checked against the actual current UI before publishing. There is no image/video upload or video library.

Signed-in users can submit a support ticket scoped to themselves and their current workspace, optionally linking a project in that workspace. They can see their own ticket statuses. System admins can read tickets across workspaces and update status. Demo guests can browse help but cannot submit tickets or save progress. Ticket text is potentially sensitive: access is limited to its submitter and global admins; do not put passwords or secrets in it. There are currently no messages/replies, attachments, email notifications, automated response-time commitments or customer-facing contact email. The admin list is capped at 200, and a user's list at 100, without pagination.

The Help assistant is extractive: it retrieves role-visible published guides, optionally lets a configured AI rank candidate IDs, validates the model output, and returns only verbatim published article text. It never exposes the model's generated prose as an answer. Keyword fallback is used when AI is disabled or unavailable, and no match is reported honestly. Results can still be irrelevant or incomplete; users should consult the linked article or submit a ticket. To opt in to AI ranking, set `HELP_AI_ENABLED=true` and configure the existing OpenAI-compatible `AI_BASE_URL`, `AI_MODEL` and optional `AI_API_KEY` securely. Only the user's question, current workspace role and matching published help text are sent to that provider; no project or ticket records are sent automatically. The UI warns users not to include sensitive information. The endpoint is rate-limited, but production multi-instance deployments should use shared/edge rate limiting. There are no AI credits or plan-based allowances.

## Deployment and verification

Deploy application code and run migrations 012–019 in order using the existing migration process; never edit a migration already applied in a deployed environment. The migrations and support system require PostgreSQL. Back up production data before migration, and review SMTP/reviewer security configuration separately in `EXTERNAL_REVIEWS.md`. These changes have been tested locally, not deployed. For isolated integration testing, run `apps/server/scripts/education-help-smoke.mjs` with `EDU_HELP_TEST_URL` and `EDU_HELP_TEST_DB` pointing to a disposable local test server/database; it creates test users and records. Run `npm run typecheck`, `npm test`, and `npm run build` as well.
