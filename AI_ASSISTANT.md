# AI Assistant: implementation and operating limits

## What is available

The authenticated `/assistant` interface is in the main navigation (including mobile and collapsed navigation). Personal conversations, messages and proposed actions are stored by user and workspace. Conversation project context is fixed on creation; start a new conversation to choose a different project. Users can search their conversation titles and their own messages, rename, delete or clear conversations. Project deletion cascades to its conversations; completed action audit records remain until their workspace or actor is deleted. Temporary demo users see the navigation entry but cannot use the assistant.

Project summaries and outstanding issue lists are deterministic and based on the selected workspace project; they link back to recorded issues and do not use model credits. Help answers quote relevant published articles and link to them; audience checks apply, and historical assistant answers that reference an unavailable or subsequently changed guide or issue are redacted on retrieval. For other questions, an explicitly enabled AI provider can generate a response from a bounded set of relevant issue summaries in the selected project, matching permitted published help and the last four user questions from that conversation. Model text is labelled as an interpretation. Previous assistant replies are not fed back into the model, avoiding propagation of help content that later becomes unavailable. The app does not yet store engineering requirements, documents, verification evidence, milestones or Education-specific roles; the assistant cannot verify or retrieve them.

The supported write proposals are `Create a new engineering project called <name>`, and, with project context, `Create a task called <summary>` / `Create a task for <summary>` and `Set task <PROJECT-123> status to <Open|In Progress|Done>`. The action shortcuts prefill these commands so users can enter their own details. Status proposals show the old and new value and fail if the title or status changed before confirmation. They create pending proposals, not records. The explicit confirmation endpoint rechecks workspace membership, current role and project, serializes execution and records the actual result; retries are idempotent. Project creation is restricted to workspace owners/admins; task creation uses the existing workspace-member policy. No model output can invoke a tool or choose an arbitrary API. Other write and destructive actions are not supported. Commands use deterministic matching rather than giving the model permission to operate arbitrary endpoints.

## Model configuration and token accounting

AI generation is **off by default**. Set `ASSISTANT_AI_ENABLED=true` on the backend and configure `ASSISTANT_PROVIDERS` as a JSON array of up to four objects with `name`, `baseUrl`, `model` and `apiKey` fields, in fallback order. Alternatively, omit `ASSISTANT_PROVIDERS` and use existing `AI_BASE_URL`, `AI_MODEL` and `AI_API_KEY`. Only HTTPS provider URLs or local loopback HTTP URLs are accepted. Do not commit keys. Keep secrets in the hosting platform's protected environment and configure `APP_URL` correctly. Questions, selected relevant issue summaries and matching published help may be sent to the selected provider; the interface warns users not to include secrets. Configure provider retention and privacy policies before enabling.

### Google AI Studio (Gemini)

Revoke/rotate any keys shared in chat or exposed elsewhere. Store replacement keys only in protected backend environment settings. Set `ASSISTANT_AI_ENABLED=true`, `ASSISTANT_GEMINI_MODEL` to a text model currently supported by your Google AI Studio project, and `ASSISTANT_GEMINI_API_KEY_1` through `_4` for up to four keys. At least one key and a model are required. The assistant uses Google's [OpenAI-compatible endpoint](https://ai.google.dev/gemini-api/docs/openai); Gemini key slots are tried in order under the existing fallback and accounting rules. `ASSISTANT_PROVIDERS` takes precedence if set; with no Gemini keys, the existing `AI_*` fallback applies. Never put secrets in a browser bundle, commit or shared logs. Verify Google project billing, quotas, access, model availability and data-retention terms before enabling. Different keys may share a project quota, so fallback does not guarantee additional quota. Successful live Gemini connectivity is not verified by the local test provider.

A global system administrator can grant explicit provider-token credits under **Admin console → Assistant token allowances**. Each new workspace starts at zero; there is no automatic free or unlimited model allowance. Before each provider attempt the service atomically reserves a conservative token budget from that workspace; on a successful response it settles against the provider's reported `usage.total_tokens`. Provider 401/403/429 responses release the reservation before trying the next configured provider. Transport failures, server errors or malformed/unaccounted responses retain the reservation as `uncertain` for administrator review because the provider may have incurred a charge. Attempts, model, user and token totals are recorded; no prompt, response, key or provider error body is written to the usage log. A provider-reported overrun is charged even if the workspace balance becomes negative, blocking later reservations. Reservations remain reserved if the process terminates mid-request; operators must reconcile them against the provider and, if appropriate, grant a compensating amount. The admin screen shows recent attempts. There is no automatic reconciliation or settlement for abandoned reservations.

These are explicitly granted token allowances for this assistant, **not** a subscription, a payment purchase, plan entitlement, dollar value or the application's other AI features. The legacy graph, Help and voice AI routes do not yet share this ledger. There is no subscription billing, payment integration or extra-credit purchase flow. Do not describe the token balance as a paid subscription balance or enable other AI features assuming this ledger limits them. Process-local per-user rate limits require shared or edge rate limiting for multi-instance deployments.

## Safety and current limitations

All conversation and project queries are scoped server-side to the authenticated user and active workspace. Help articles are checked against the caller's current role and publication status. Provider credentials remain on the server. Model output is treated as untrusted advice and cannot execute writes; a user must confirm each supported proposal. Prompt injection can still influence natural-language advice, so users must review results. Owners/admins and members are the only workspace roles; institutional and student separation, document permissions, attachments, OCR, semantic document search, voice conversation, response streaming, model-led tools and educational entitlements are not implemented. No record source may be inferred to exist merely because the model discusses it. The interface renders Markdown as text/formatting without active AI-generated links or images and displays server-selected source links separately.

Deploy migrations `020_assistant` and `021_assistant_status` together with backend and frontend code. The `021` rollback intentionally fails if status-action audit records exist; it never deletes them automatically. Test only on a disposable database: `ASSISTANT_TEST_URL=http://localhost:4000 ASSISTANT_TEST_DB=postgres://... node apps/server/scripts/assistant-smoke.mjs` assumes the local test API has two configured test providers, one returning 429 and the other a fixed response with usage. The additional `assistant-status-smoke.mjs` checks status actions against the same disposable server/database. Never point these tests at production. Also run `npm run typecheck`, `npm test`, `npm run build`, and permission/responsive checks. See `SECURITY.md` for password-reset SMTP configuration added in the same release.
