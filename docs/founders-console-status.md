# Founders Console — security boundary and remaining work

**Status: not implemented; not safe to enable.** `/founders` is only an unavailable notice, not a sign-in screen. `/api/founders` and its descendants are reserved and always return 404, independently of ordinary account sessions. No founder account has been created, and no owner-supplied secret has been obtained or stored. No existing account is elevated by matching an email address. Do not remove the guard or treat this placeholder as a release.

## Findings from the existing application

- Workspace authorization is based on membership and `owner`/`admin`/`member`; ordinary system administration uses `users.is_admin`. Neither is a founder identity. Existing `requireAdmin` must not protect a founder operation on its own.
- Existing passwords use scrypt, ordinary session tokens are hashed before storage, and the server checks origin on mutations. The existing account login has IP limiting and account lockout. These are useful building blocks, but they are not a dedicated founder session, MFA, or a founder audit system.
- The server automatically applies registered migrations at startup. A schema migration for a future console must be additive, reviewed, tested against a disposable copy, and assessed for deployment impact. Never run the destructive down migration for native sketch documents.
- The regular admin endpoints expose broad platform data and operations. Do not proxy them wholesale to a founder UI: every operation needs an independently verified server-side policy, redaction, reauthentication where appropriate, and durable audit.

## Required implementation gates (all still open)

1. Design and independently review an isolated founder identity and session model, separate from workspace and system-admin credentials. Centralize authorization for *every* protected operation, including direct API requests. Use secure cookies, short lifetime, rotation and server-side revocation; handle expiry and concurrent revocations correctly.
2. Implement controlled one-time bootstrap for the designated owner identity. The bootstrap password must come solely from an owner-provided protected deployment secret, be hashed using the existing password infrastructure and never be logged, committed, put in a URL, or sent to the frontend. A matching ordinary account must not be granted founder rights without explicit, separately authorized identity verification. Enrollment must require a password rotation and MFA before any privileged access. Define a recovery and secret-removal procedure before production use.
3. Implement MFA, preferably WebAuthn, with an appropriately secured alternative and recovery; protect enrollment, challenges, replay, concurrent authentication and reauthentication for sensitive actions. Add shared/distributed rate limiting, account lockout, suspicious-login monitoring and operational alerting. Harden origin/CSRF, transport, caching and logging for this boundary rather than relying on UI navigation.
4. Create a durable append-only founder audit trail with unique event ID, actor and role, action, target, timestamp, redacted before/after, reason, request ID and result. Commit audit and successful state changes atomically; retain failed attempts safely, prevent ordinary founder deletion, restrict database privileges, and document what database administrators can still do. Never record credentials, tokens, MFA material or customer repository content.
5. Add secure founder invitations, session and account management; real platform overview, account/workspace management and access requests; role/permission handling; and configuration/integration status only for capabilities that exist. Verify each operation's data exposure, tenant boundaries, confirmation, reason, reauthentication and audit. No arbitrary SQL, infrastructure access, fabricated subscription data or exposed secrets.
6. Run migrations, tests and independent browser/API authorization and revocation checks on disposable infrastructure. Test anonymous, ordinary users, workspace admins, system admins, revoked/expired sessions and cross-origin requests. Check secrets and deployment impact before any release; do not deploy to production without authorization.

## Evidence for the current reservation

`founders-boundary.test.ts` tests the guard on the real Express application using an unreachable database, for multiple HTTP methods, paths, origins and synthetic ordinary-session cookies. The separate `apps/server/scripts/founders-boundary-smoke.mjs` uses a disposable local database and real ordinary sessions for anonymous, workspace owner, workspace admin, member, system admin and logged-out users. It checks the namespace is closed and verifies the system admin can use the *ordinary* admin overview while a workspace admin cannot. A disposable browser check confirmed the unavailable page and a descendant show no login inputs and make no API or analytics requests. These checks do not prove the security of a future console or any founder session. There is no founder authentication, MFA, recovery, bootstrap, audit, or operational UI to test yet. The guard is explicitly intended to be replaced by a separately reviewed security boundary, not used as one.
