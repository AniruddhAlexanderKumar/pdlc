# Founder authentication — work in progress, not production-ready

**Founder security is incomplete. Do not enable or use founder authentication with real credentials.** The user authorized pushing this branch despite unresolved gates and the possibility of automatic deployment and migration; that decision is not security acceptance, and the actual deployment state is unverified. The production API remains denied. A deliberately opt-in, non-production-only authentication experiment exists to exercise the unfinished lifecycle. A separately opted-in local customer-management slice has been added; see `founders-customer-dashboard.md` for its exact scope and limitations. The shared PostgreSQL throttler and internal SMTP primitive are partial, not production-ready; recovery orchestration/UI, controlled Owner recovery, independently authorized bootstrap, deployed audit privilege separation and monitoring remain missing. See `founders-part-1-2-review.md` for the security checklist, evidence, blockers and migration runbook; it predates the customer-management slice.

## Existing security and migration assessment

The earlier deny-all boundary is commit `3e06cac`. The normal application has scrypt passwords, hashed session tokens, process-local IP rate limiting and account lockout, and origin checking. It has no pre-existing founder MFA or founder security audit. Normal `users.is_admin` and workspace memberships are not founder privileges. The normal origin middleware accepts requests without an Origin; the experiment uses a stricter, separate exact-Origin and JSON guard. Ordinary SMTP settings exist; an unexposed founder mail primitive has passed a local SMTP sink test, but there is no end-to-end recovery workflow or external delivery verification. The experimental founder router is mounted ahead of the general request logger and uses a sanitized error handler; recognized PostgreSQL errors in the general handler and startup logging are also sanitized. This does not prove every logging or telemetry channel is safe.

Migration **027** adds founder accounts, a singleton bootstrap state and audit table, and triggers blocking ordinary UPDATE, DELETE and TRUNCATE of audit records. It is additive and does not alter ordinary authentication tables. Its down migration intentionally throws rather than delete security records: this avoids accidental data loss but is **not an automatic rollback**. The bootstrap transaction briefly takes a SHARE lock on `users` to serialize the matching-email collision check with ordinary registrations. Migration **028** adds encrypted-secret, challenge, session, recovery-code and password-recovery storage, and refuses automatic destructive down migration too. An existing active founder lacking a TOTP ciphertext would make 028 fail intentionally; databases that applied an earlier draft need inspection, not an assumption that they match this source.

Disposable PostgreSQL tests upgraded a database at migration 026 with an existing ordinary authenticated session, simulated a conflicting table causing a migration failure, checked transactional rollback, retried successfully, reran idempotently, and confirmed down migration refuses to delete security state while ordinary authentication still worked. These tests do **not** prove production migration safety. Server startup automatically applies registered migrations. A safe release requires an existing-schema and privileges review, compatible PostgreSQL version, verified backup/restore, a rehearsal on a representative isolated copy, monitoring and a forward-fix plan. The user authorized this branch push even if it triggers automatic deployment or migration; actual production execution is unverified.

## Local-only experiment

The default `/api/founders/*` deny-all guard remains. Only when `FOUNDER_AUTH_EXPERIMENTAL=true` **and** `NODE_ENV` is not `production`, the application mounts the following test-only endpoints before that guard:

- `POST /api/founders/login`, `/mfa/setup`, `/mfa/verify`, `/password/rotate` and `/logout`.
- `GET /api/founders/me` requires a valid active founder session with the operations-read permission. With a second explicit local/test-only management flag, customer and workspace list/create/status routes are enabled; all other management paths remain blocked, and every founder path remains denied in production.

The separate browser UI is included only when the web build explicitly sets `VITE_FOUNDER_AUTH_EXPERIMENTAL=true`. In that local build the ordinary `/login` page routes the confirmed Owner identity through the separate founder password/MFA flow; it does not authorize by email. See `founders-customer-dashboard.md` for fallback and collision behavior. Otherwise the existing unavailable notice stays in place and ordinary sign-in is unchanged. The experimental UI is clearly labelled, shows a manual TOTP setup key and one-time recovery codes, and does not offer an operational recovery flow. It stores no founder tokens in browser storage. Browser lifecycle and API tests used only disposable databases and synthetic, randomly generated credentials. The experimental API test also checked that a real ordinary system-admin session cannot access founder `/me`, five failed password attempts lock the founder account without subsequent attempts extending that same deadline, and the shared DB-backed IP limiter returns 429. The account-wide lock remains vulnerable to repeated targeted denial of service. A separate session test exercised all three role policies, suspension, version revocation, expiration and CSRF. Neither test verifies production readiness.

The experiment creates short-lived, hashed restricted flow tokens after password authentication; only MFA-verified pending users can rotate the temporary password, after which a fresh hashed session token is issued. Existing founders must verify TOTP or a single-use recovery code after password authentication. TOTP uses OTPAuth and AES-256-GCM with an externally supplied 32-byte key, with account ID as associated data; accepted TOTP time steps are tracked to reject replay. Recovery codes are randomly generated and stored only as SHA-256 hashes. Dedicated founder cookies are HttpOnly and SameSite=Strict, with Secure enabled for HTTPS. Session validation rechecks account status, role, MFA enrollment, rotation state, session version, idle expiry and absolute expiry. The service-level authorization function must be invoked inside the same transaction as any future privileged mutation; the middleware alone is not enough to prevent races. Password rotation increments the session version and deletes previous sessions and flows.

Roles and preliminary permissions:

| Permission | Owner | Admin | Operations |
| --- | --- | --- | --- |
| Founder identity/security/roles | yes | no | no |
| Future platform accounts/configuration | yes | yes | no |
| Operations read | yes | yes | yes |

Self-role changes and unknown role/permission strings are denied by policy utilities. No founder-management mutation exists. These grants are not proof that future account or configuration operations are safe; those services must independently enforce permissions and auditing.

## Bootstrap test command — not for production

A restricted CLI is present solely for disposable local testing. It refuses `NODE_ENV=production` and requires `SV_FOUNDER_BOOTSTRAP_ENABLED=true`. The identity is `f5manmission@sv.com`. It requires a migrated disposable `DATABASE_URL` and these externally supplied environment values:

- `SV_FOUNDER_BOOTSTRAP_NAME` — display name.
- `SV_FOUNDER_BOOTSTRAP_PASSWORD` — temporary password, never supplied as an argument or committed.
- `SV_FOUNDER_BOOTSTRAP_SECRET` — high-entropy submitted secret.
- `SV_FOUNDER_BOOTSTRAP_SECRET_SHA256` — expected lowercase SHA-256 digest, which must be provisioned independently from the submitted secret in any future trusted design.

After provisioning those values through a protected process environment and applying migrations to a disposable database, the test command is `npm run founder-bootstrap --workspace @sv/server`. Do not paste values into shell history, source, logs or chat. This is **not an approved production procedure**: a caller able to override both digest and submitted secret can choose matching values, so an operational design must establish independent protected configuration, restrict operator and database privileges, and remove all bootstrap secrets after consumption. The CLI does not apply migrations itself. It refuses matching ordinary accounts instead of assuming ownership, serializes concurrent attempts, writes a pending owner and audit event, and marks bootstrap consumed atomically. The test-only command does not itself establish MFA or provide recovery; using it against a real system could strand an owner.

For local authentication tests, the server also needs independently generated `SV_FOUNDER_TOTP_KEY` and `SV_FOUNDER_RATE_LIMIT_KEY` values, each a protected, canonically base64-encoded random 32-byte key. The latter is also required by the local bootstrap CLI. Do not reuse keys. Losing or changing this key without a migration/recovery plan makes stored TOTP secrets unreadable. The key must not be checked into files, logged or sent to the browser. Never reuse the example/test process or keys as a deployment procedure.

## Recovery and audit gaps

An unexposed recovery primitive stores short-lived token hashes, invalidates prior tokens, rejects Owner accounts, consumes tokens once under concurrency, revokes sessions and still requires MFA at the next login. A separate unexposed self-reset primitive requires an existing founder session, password and fresh TOTP, invalidates sessions and recovery codes, and returns the account to pending enrollment. It is not a recovery process for someone who has lost the authenticator, and its operational integration and rate limiting remain unimplemented. There is **no public recovery endpoint, no verified email delivery, no recovery UI, and no operational Owner recovery**. If the owner loses MFA, a future process must require independently verified owner identity, at least two explicitly authorized operators, out-of-band approval, documented incident/change control, revocation of all old sessions and factors, protected re-enrollment, and durable audit. No such recovery operation is available today; do not manually edit the production database as a substitute.

The audit table records bootstrap and selected experimental lifecycle events and now restricts event names, but does not yet implement all required metadata, reason, alerting or independent retention. The mutation trigger cannot prevent a database owner or superuser from altering it; Compose currently uses an owner role for the app. An isolated non-owner role test confirms that UPDATE, DELETE, TRUNCATE and trigger changes can be denied, but the deployed role separation is not established. Before release, establish independent ownership, least privileges, and independently controlled durable audit storage.

The original constraint-violation reproduction logged a synthetic founder password hash through PostgreSQL DETAIL. A follow-up PostgreSQL 17.9 test with the checked-in Compose flags and sanitized founder handler proved that the synthetic sentinel was absent from captured server/app logs and the HTTP response, while SQLSTATE and a test request correlation ID remained available. This is not proof for the unknown deployed DB configuration, arbitrary SQL literals or error messages, driver instrumentation, CI or external collectors; real founder transactions do not yet propagate the correlation ID to PostgreSQL. End-to-end production log safety remains a release blocker.

## Remaining gates

- Complete and independently review production bootstrap authorization and an approved Founder Owner recovery and MFA reset process.
- Implement and test generic, rate-limited founder password recovery delivery without bypassing MFA; prove actual delivery before claiming it works.
- Complete distributed rate limiting for recovery and reset, limiter retention and proxy trust, address the account-lockout denial-of-service risk, add suspicious-login alerts, complete audit events and safe DB privileges, and verify all session/MFA-change revocation and reauthentication paths.
- Complete exhaustive API/browser security tests including simultaneous changes, all roles, cross-account isolation and failure modes. Keep all management endpoints blocked until their own services are authorized and audited.
- Do not represent this unfinished Part 1 as a completed authentication release or enable founder authentication in production.
