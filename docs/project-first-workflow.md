# Project-first workflow — initial slice

The application now directs ordinary sign-ins without an explicit `next` destination to the project chooser. System-admin and founder sign-ins retain their existing destinations; deep links, invitation flows, signup, password reset and the temporary demo retain their existing behavior. Users can create a project if their workspace role permits it, or select an existing project and switch projects later. A project overview provides the existing project issue screen and lists/creates conceptual diagrams explicitly associated with that project. The diagram list is limited to the 200 most recently updated in that project.

The existing workspace dashboard, product lifecycle records, catalogues, voice import, assistant, design list, graph, settings and direct URLs remain accessible. This is deliberately **not** a claim that all workflows are project-scoped, that selecting a project restricts other tools, or that a project is a separate permission boundary. Existing server authorization is workspace-based; workspace members can access project records as currently permitted. Project-associated diagrams retain their existing creator/owner/admin edit rules. No automatic assignment, merging, moving, deletion or duplication of older data occurs. The filtered design API validates the project against the authenticated workspace and retains its unfiltered behavior for existing clients. No database migration is introduced.

The new overview and issue screen warn before abandoning unsaved new-diagram names or issue drafts through in-app navigation, tab unload, workspace switch or sign-out. They prevent navigation during an in-flight create; a failed or lost create response is explicitly uncertain and users should check the list before retrying. These warnings are not durable draft storage or a guarantee against browser crashes, all interruptions, duplicate requests, or data loss. Saved design revisions continue to use the existing optimistic conflict checks. Project issue edits and other modules retain their existing behavior.

Full project-specific workflows require further design and implementation: choose explicit ownership or shared relationships for existing products, materials, suppliers, design/CAD documents, voice imports, AI conversations and dashboard views; preserve unassigned and shared records; enforce the chosen scope on the server for every read, write and AI action; define project-level access policies rather than treating a UI selection as authorization; handle switching, drafts, concurrent edits and uncertain saves; and test empty, multiple-project, cross-workspace, shared-record, migration and recovery scenarios. No existing workspace data should be silently reassigned. Deployment and any future migration need separate review and authorization.
