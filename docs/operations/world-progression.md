# World progression: cutover and verification

Solution Velocity’s product journey runs in **`apps/web` (Vite/React), `apps/server` (Express/Kysely) and the existing PostgreSQL database**. The root `Dockerfile` builds both workspaces. The Pages workflow publishes the pitch, not this service. A Git push does not migrate or deploy `pdlc.dalvigroup.co.in`.

## What changed, and where to look

| Area | Source of truth | Effect of this release |
| --- | --- | --- |
| Identity, permissions, billing | Existing sessions, memberships, roles, workspace/assistant credit systems | No new identity or paid currency. Use the same account, session and products. XP cannot buy provider credits. |
| Product curriculum | `packages/shared/src/{questions,journey,worlds,gamification}.ts` | Eight worlds, each with three stable units. Lessons refer to actual answer keys or product tools; optional exercises do not block a checkpoint. A saved assumption is not a sourced finding or build trial. |
| Deliverables | Existing answers/briefs, approvals, notebook, tasks, prices/costs, BOM, design revisions and product CAD | Exact field matches may populate missing answers. Other explicitly linked work offers bounded excerpts for **review**, not invented completion. Project-only and workspace-only documents are not assigned to an arbitrary product. |
| Entry and navigation | Building desk, `/products/:id/journey`, `?stage=…` detail and existing editor routes | A selected active product opens its path. Expand any world to see its goals and lock reason. Existing workspace widgets, saved layouts, studio, analytics and record editors remain accessible. Archived products retain their records. |
| Reward writes | `routes/util.ts`, `services/{xp,world-trail,save-answer,reward-rules}.ts` | Real product mutations, their receipts and period rewards commit together. Product work is shared. The individual who supplied the completing change gets the first eligible credit; another member cannot replay it. |
| Coach | Existing lesson assistant, provider routing and credit meter | Adds the selected unit, missing checkpoint requirements and bounded related document excerpts. The rules-based guide also works without a model. Suggestions change nothing until reviewed and submitted. |

## Recognition is not a new accomplishment

Migration **`036_world_progression`**, release key **`worlds-v1`**, runs after `035_founder_journey`. Keep both migrations in the Kysely manifest, including the bundled runtime. The migration runs under the migration transaction/lock, scans products in batches of 100, and freezes the original required-node manifest. This bounds each read, **not** the duration of the database transaction.

- Preserve the original stage string in `journey_upgrades`. Canonicalise known spellings; use actual visits for reachability. For an unknown stage, suggest a position from the last known visit, then existing answer/task chapter keys. An owner/admin can confirm the placement **once**, without points. Old archive access is not evidence of eight completed worlds.
- Copy a nonempty, compatible description into a **missing** one-line concept; a non-default category, explicit target price or positive overhead into its corresponding missing answer. Keep existing answers, authors, dates, approvals and drafts. A copied answer records its recognition time, has no invented author, and is listed in `imported_keys`. Zero is legitimate where explicitly recorded; an old default zero is not proof that someone estimated overhead.
- Read checkpoint evidence, including explicit sign-off on the customer-validation decision, design specification and test criteria. A prior world milestone requires eligible evidence, a historical checkpoint transaction and recorded forward movement. A later stage alone is **access**, not a badge. Dependency-bearing work is conservatively rechecked against live dependencies. Malformed saved answers, unlinked tasks and uncertain notes remain reviewable, not silently discarded.
- `journey_stamps` stores one receipt per product and stable node. Historical receipts have `origin=recognised` and no attributed actor. Keep the old XP rows, IDs, earners, amounts and timestamps (`origin=legacy`); the migration issues **zero retroactive XP**. Prior team-wide Margin Master/Supplier Scout entitlements are marked `legacy_team`, not reissued as personal work. A cutover flag freezes that snapshot across retries. Product paths and private drafts never merge across users or products.
- The live map distinguishes completed, in progress, needs review, not started and legacy recognition. Reviews/edits can make evidence incomplete without taking away an earlier receipt, badge or XP. Use **Use existing work** to inspect a linked note or a small `.txt`/`.md` excerpt. There is no automatic parsing of arbitrary PDFs or CAD files and no external verification of the founder’s claims.

## XP, quests and streaks

The permanent ledger is **personal within the current workspace**, across its products. A product’s checkpoint is shared; a person does not inherit the rest of their team’s XP. Workspace competition uses the existing opt-out; solo mode has no ranking. First lesson credit is keyed by product + question across the team. Historical sections recognised at cutover do not pay first-submission XP on later edits. Units/checkpoints/worlds use stable node keys; the legacy `quest_complete` kind is the checkpoint, not a second payment. Closing the world opens the next new world on the guided path. A forward stage advance is a separate action; the existing stage editor can recheck, finish and advance in one transaction. Guided writes check locks and assignments; record editors remain available outside the guided sequence.

Defaults: per-question credit **5–30**, unit **50**, checkpoint **100**, world **200**, daily **20**, weekly **75**. Badges are honours, not another payment for the same work. An operator may supply a server-only `BUILDER_XP_RULES` JSON object, e.g. `{"unit":60,"weekly":90}`. Optional keys: `normalLesson`, `substantialLesson`, `deliverableLesson`, `unit`, `checkpoint`, `world`, `daily`, `weekly`; integer values 1–1000. Restart the app to change future awards. Existing transactions are never repriced. Quiz answers, client amounts, page views, repeated saves and AI suggestions are not independent reward claims.

Daily quests use the stage at **00:00 UTC** (or initial placement for a new product). Idea asks for two first credited outputs; later stages ask for a particular set of outputs, such as research evidence or test reporting. Weekly quests run Monday–Monday UTC: one unit/checkpoint or two completed product tasks. Both are scoped to **member + product + period**. Levels start at `50 × L × (L − 1)` cumulative XP. Streaks use UTC dates with an XP event or a changed, nonempty submitted answer, including revisions without XP; yesterday’s streak can still continue today. The journal shows the last 35 dates, run and level histories and paginates the full private ledger. Existing streak preferences are preserved; new accounts initially show streaks.

## Rehearse before applying to a customer database

1. Identify the running app revision, PostgreSQL schema/version, runtime and migration roles, available storage and approved maintenance window. Take a consistent, access-controlled backup **and test its restoration into an isolated database**. Keep the matching pre-release app image. Do not export private documents, credentials or dumps to this repository. If production is older than 035, rehearse the intervening migrations first on that restore.
2. Point a read-only connection at the isolated **035** restore and run `npm run journey:report` (built image: `node dist/scripts/journey-report.js`). Save the `pre-036` inventory privately. Agree on representative existing products to inspect, including partial/malformed work, approvals, an inactive member, unlinked tasks, archived and multi-product cases. Disable outbound provider/email side effects on the restore.
3. Using a migration role **on the restore**, run `npm run migrate` (image: `node dist/scripts/migrate.js`). Run it again: no pending migration. Run the report again. Compare account/workspace/membership/product/task/draft/sign-off/design/revision/CAD counts and XP row count/sum. Before any user writes, the answer count difference should equal `exact_field_matches`; old XP should equal the legacy subtotal. Investigate unexplained deltas rather than continuing. Review `positions_to_confirm` and `tasks_needing_placement` separately; they are not completions. Inspect sample products using the actual application. Measure duration, locks, disk and query latency on production-sized data.
4. After rehearsal and owner approval, pause writes/old app instances, take the final recovery point and repeat the checks using the existing controlled deployment flow. Start the matching build with **`MIGRATIONS_ON_STARTUP=false`** and the ordinary restricted runtime role. Check `/api/health`, login with an existing account, resume a mid-stage product and verify one real checkpoint/retry before reopening access. Preserve `APP_URL`, secrets, provider, SMTP, storage and billing settings. Do not run destructive fixture scripts on this database.
5. Failure before migration commit: keep writes paused, inspect the recorded migration result and retry the corrected forward migration. Failure afterwards: prefer a reviewed **forward fix**. `036.down()` deliberately refuses to delete progress. If a restore is unavoidable, restore the matching snapshot/image into a separate recovery environment, reconcile subsequent legitimate writes, and switch over under your recovery procedure. Do not reset a live database or run an old writer alongside the new one.

### Reproducible synthetic checks (disposable localhost only)

`npm run typecheck`, `npm test`, `npm run build`. The PostgreSQL job in `.github/workflows/ci.yml` sets up both populated upgrade tests, runs the real API and Chromium tests and checks the production Docker image. `worlds-upgrade-smoke.mjs` requires an empty local `worlds_upgrade_test` (or suffixed test name); `WORLDS_UPGRADE_BROWSER=1` also exercises the old login in Chromium. `worlds-smoke.mjs` covers concurrent team claims, scope, placement, retries, evidence revisions and paginated history. `journey-smoke.mjs` drives a product through **all eight** world finishes. `journey-browser-smoke.mjs` covers registration, importing a reviewed note, activity editing, a real world finish, advancing, and the builder journal. Only use these scripts with the isolated test settings described in CI.

**Measured fixture, not production data:** two members, three products, nine original answer sections, a private draft, an approval, one unlinked task, one product diagram/revision and 11 transactions totalling 250 XP. Post-cutover: same records, three missing exact fields filled (12 answer sections), five recognised units, one recognised checkpoint and one recognised world. Both Kysely retry and direct migration retry retained 11 transactions / 250 XP. No one was asked to repeat Idea to access Testing or Launch. The third product had an unfamiliar stage; an explicit one-time repair updated placement without XP. Production size, lock time, delivery and deployment must be checked by the operator.
