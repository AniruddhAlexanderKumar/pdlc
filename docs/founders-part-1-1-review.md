# Founder authentication Part 1.1 — security review and release gate

Historical assessment: the Owner email mentioned below was the identity under test at the time. The subsequently confirmed local bootstrap identity is `f5manmission@sv.com`; changing the source does not modify any existing account.

**Status: BLOCKED.** Experimental changes are uncommitted and must not be deployed. Production `/api/founders/*` remains denied and the bootstrap CLI refuses production. No production database, credentials, deployment, or migration was touched. This is not a management console or approval to ship. The following separates verified results from remaining requirements.

## 1. PostgreSQL disclosure and scope of correction

The reproduced operation is `UPDATE founder_accounts SET status = 'active'` against a pending founder without TOTP, violating `founder_active_has_totp` (SQLSTATE 23514, migration 028). PostgreSQL 18.4 default logging printed the failing row's synthetic scrypt hash in server `DETAIL`. On PostgreSQL 17.9, a disposable regression recreated the same constraint failure and confirmed the driver still receives that DETAIL. Using the flags checked into Compose, the sentinel was absent from captured DB logs, sanitized founder application logs and the synthetic HTTP response; SQLSTATE and a request ID were retained. The test sets PostgreSQL `application_name` explicitly; actual founder transactions do not yet propagate that ID.

Compose sets `log_error_verbosity=terse` (omits DETAIL/HINT/CONTEXT), `log_parameter_max_length=0`, `log_parameter_max_length_on_error=0`, `log_min_error_statement=error`, `log_statement=none` and `log_min_duration_statement=-1`. Keeping error statements aids diagnostics but SQL text with inline literals can still disclose secrets; TERSE does not sanitize arbitrary error MESSAGEs, extensions, connection errors, triggers, driver/APM instrumentation or other collectors. Avoid embedding sensitive values in SQL. The sanitized founder error handler emits only server-generated request ID, category and optional SQLSTATE; recognized DB errors in the general handler and startup are also sanitized. These changes do not establish full telemetry redaction. Actual deployment DB version/settings, all destinations, CI collection, alternate query paths and production correlation propagation remain unverified. Repeat the sentinel test against an isolated clone of the independently reviewed intended deployment configuration and inspect every applicable channel before release. Do not connect tests to production.

## 2. Distributed throttling

Migration 029 provides persistent HMAC-keyed PostgreSQL buckets. Atomic upserts use the DB clock, an IP and an account-plus-IP dimension, capped exponential cooldown, `Retry-After`, and fail closed on database errors. The experimental login, MFA enrollment/verification, password rotation and local bootstrap CLI use it. The shared bucket concurrency test used four separate processes as well as independent connection pools; exactly 10 of 60 simultaneous attempts were admitted, a subsequent fresh process saw the cooldown, cooldown increased after expiry, and DB failure rejected the operation. The API test also confirmed 503 when the table was unavailable. MFA recovery codes share verification throttling in the experimental route.

This is **not a complete distributed protection**: recovery and MFA-reset primitives are not routed or limited, rate-limit alerts/monitoring and bucket cleanup do not exist, rate-key rotation resets existing buckets, limits are not independently tuned/load tested, and the existing five-failure account-wide lockout can be abused to deny service to a known founder from many IPs. IP-only limits can also hurt users sharing NAT. Deployments must verify ingress strips untrusted forwarded headers and `TRUST_PROXY` matches the actual trusted proxy chain; incorrect trust can enable spoofing or collapse clients onto one IP. No persistent bucket cleanup policy exists, so high-cardinality abuse can grow the table; implement bounded retention after every possible active window and monitor growth before release. A public endpoint must never use a process-local fallback when the DB is unavailable.

## 3. Audit and privilege separation

Migration 027 creates a founder audit table with UUID actor/target/request, enumerated role/outcome and timestamp, plus triggers denying UPDATE, DELETE and TRUNCATE. Migration 030 restricts event names to a fixed allowlist and revokes PUBLIC privileges. The transactionally coupled bootstrap audit failure test shows a failed success-audit insert rolls back creation and bootstrap consumption. In a disposable DB, a deliberately non-owner, non-superuser test role with INSERT/SELECT could insert allowed events but could not update, delete, truncate or disable triggers; invalid event names failed the DB constraint. This tests the principle, **not the deployed application role**.

Compose currently uses one DB owner identity for migrations and application traffic. Owners, superusers and roles inheriting owner privileges can change schema, disable triggers, rewrite history or fabricate events; the application writer can fabricate allowed inserts. Triggers and a local table are not tamper-proof against privileged operators. Before release, separate migration owner and unprivileged app writer; prove it is not owner, superuser, or a member of an owner/bypass role; grant only necessary insert/read privileges and explicitly deny mutation, schema and trigger privileges; test actual deployment role memberships and cross-table privilege needs. Add independently administered, immutable/append-only export, retention, monitoring, reconciliation and alerts. Complete missing events, actor/target/correlation semantics and audit-failure tests for every sensitive transaction. No such privilege deployment or external audit pipeline was performed.

## 4. Password recovery email

The unexposed non-Owner primitive stores a 20-minute token hash, invalidates prior tokens, consumes once under row locks, rotates the password and revokes sessions/flows while preserving MFA. An internal SMTP delivery primitive uses existing `RESET_SMTP_HOST`, `RESET_SMTP_FROM`, `RESET_SMTP_PORT`, `RESET_SMTP_SECURE`, `RESET_SMTP_USER`, `RESET_SMTP_PASSWORD` and `APP_URL`; it avoids logging transport exceptions and puts a token in the URL fragment. A synthetic message was delivered via SMTP to an isolated local sink and a disconnected sink returned failure. This is **not** an external provider/mailbox delivery test and the linked recovery page does not exist. There is no public request/completion endpoint, generic-response orchestration, delivery-failure token invalidation, rate limiting, or email UI. Do not call the primitive as a working recovery service. Before release, supply a non-production SMTP provider/test mailbox and its configuration via protected secrets, implement the full workflow and generic responses without enumeration/timing leakage, and verify delivery and expiry/reuse/session/MFA behavior end to end. Do not record credentials or real token links in logs.

## 5. Owner recovery design — not implemented

No public Owner recovery/reset endpoint exists and Admin/Operations cannot reset Owner. Use independent identity verification and separately authenticated, independently controlled approvals; with multiple Owners require at least two distinct authorized approvers. For a single Owner, a separately provisioned restricted break-glass procedure should require multiple independent operators and out-of-band verification, documented incident/change authorization, time-limited access, independent audit and notification. Atomically revoke old sessions, flows, MFA secret and recovery codes, force protected MFA re-enrollment and credential rotation, and notify the Owner/security contacts through independently established channels. Define secure approval, rollback, escalation and lost-key cases and test with disposable fixtures. No operational process has been implemented or verified; do not manually modify a real database as a substitute.

## 6. MFA reset

The unexposed self-reset primitive requires a session, password and fresh TOTP, revokes sessions and recovery codes and returns the account to pending MFA enrollment. It cannot recover a lost authenticator and has no externally reviewed flow, rate limiter, notification, or complete failure/concurrency tests. Owner loss of MFA must use the independently approved process above. No public reset endpoint is enabled.

## 7. Bootstrap design — not operational

The Owner identity is `f5fmanmission@sv.com`. The local CLI is `npm run founder-bootstrap --workspace @sv/server`; it requires a disposable migrated DB, `SV_FOUNDER_BOOTSTRAP_ENABLED`, `SV_FOUNDER_BOOTSTRAP_NAME`, `SV_FOUNDER_BOOTSTRAP_PASSWORD`, `SV_FOUNDER_BOOTSTRAP_SECRET`, `SV_FOUNDER_BOOTSTRAP_SECRET_SHA256` and `SV_FOUNDER_RATE_LIMIT_KEY`. Never put actual secrets on the command line, in source or logs. The local CLI refuses production. It locks singleton bootstrap state, rejects an ordinary-user email collision, creates a pending founder and consumes state atomically with audit. It still trusts both expected digest and submitted secret from the caller's environment, so an operator who can override both can authorize themselves.

For a future release, independently provision and protect verifier material via a secret manager outside the operator's control, enforce strong operator authentication and separate approval/least-privilege database roles, and restrict the command and secret access to an approved short window. Require mandatory MFA enrollment/password rotation, atomic one-time state and audit, invalidate/revoke bootstrap material, and define safe retry after uncertain commit by checking durable state without revealing credentials. Independently rehearse failure, retry, collision, concurrency, and secret invalidation in isolation. No production-capable command is currently approved.

## 8. Migration review and locks

027 creates separate founder accounts, singleton bootstrap state, audit records and mutation-rejection triggers. 028 alters founder accounts to add encrypted TOTP and accepted step, validates active accounts, and creates flows, sessions, recovery codes and password recoveries with foreign keys/indexes. 029 creates shared limiter buckets; 030 adds the audit allowlist. They are registered in startup's statically bundled migrator. Their down functions deliberately refuse to delete security data. Never run migration 026 down: it destroys CAD data.

PostgreSQL transactional DDL is enabled in the installed Kysely adapter. Its migrator takes a session-level PostgreSQL advisory lock (with a one-hour lock timeout) and applies pending migrations within a transaction. DDL such as 028's ALTER TABLE takes strong locks and can block application traffic; validation of existing rows may fail, and other DDL can block startup. Migration result messages emitted for earlier steps do not by themselves prove commit if a later step fails. Startup exits on errors; an automatic restart can retry, so stop restart loops during investigation. An earlier draft with active founders lacking ciphertext or an unexpected existing schema can fail. Audit allowlist validation can fail for existing nonconforming events. Never blindly edit historical migrations already applied; use an independently reviewed forward migration.

Disposable PG17 tests covered clean install and simultaneous migrators, existing 026 data/ordinary session, name conflict in 027, partial 028 failure with all 028 changes rolled back, retry, repeated migration and refused down. Simultaneous first initialization produced duplicate migration-metadata table/lock-row errors in PostgreSQL logs; Kysely recovered from those races and both callers completed with each migration recorded once. They do not prove behavior with a representative production dataset, unusual existing schema, live traffic, failover or actual permissions.

1. Do not execute now. Obtain explicit approval; identify the deployed image, exact DB/version/settings, existing migration history/schema and drift, ingress, credentials and role ownership. 2. Verify a recoverable, encrypted backup and a tested restore, retention and recovery point/time objectives. Check logging redaction and independent audit readiness. Keep founder APIs and production bootstrap disabled.
3. Schedule a window with monitoring and named rollback/forward-fix decision makers. Run one approved migration operator with narrowly scoped owner permissions; do not provide migration ownership to the runtime role. 4. A verified backup does not itself authorize a restore or deployment.

## 10. Password hashing

Existing scrypt is retained: N=32768, r=8, p=1, random 16-byte salt, 64-byte output, stored parameters, NFKC normalization and timing-safe comparison. Tests check salts, correct/incorrect passwords, normalization and stored parameters. Password-hash corruption/hostile parameters, performance under load and future work-factor policy deserve further review; there is no basis here to replace scrypt merely to match an earlier Argon2 recommendation.

## 11. Session and authorization

Founder cookies are separate from normal sessions, HttpOnly and SameSite Strict, Secure on HTTPS, with hashed tokens, 30-minute idle and eight-hour absolute expiry and account/session-version/MFA checks. The experiment uses exact Origin plus JSON checks for writes, restricted pre-MFA/rotation flows, TOTP replay prevention and one-time recovery codes. Isolated tests cover ordinary-admin isolation, role checks, suspension, expiry, session version, CSRF, rotation and logout. These are local-only results, not comprehensive concurrency or penetration testing. Future privileged service mutations must authorize and audit in the same transaction. No founder-management routes exist.
