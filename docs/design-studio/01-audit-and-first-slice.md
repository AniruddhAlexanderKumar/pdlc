# Design Studio: audit and initial slice

## Audit
The current React/Vite app has an authenticated workspace layout; Express checks active workspace membership and uses PostgreSQL/Kysely migrations. Products and projects are separate workspace-scoped records; issues belong to projects. Requirements, engineering decisions, verification, GitHub integration and design documents do not currently exist as first-class records. Demo sessions have restricted APIs. A substantial unrelated working tree must be preserved and reviewed separately. The existing CAD research and licensing approval gate remain unchanged.

The installed `@xyflow/react` 12.12.0 declares MIT licensing and is already used for Teamwork Graph; it can be evaluated for later editing. React declares MIT. A bounded SVG/form editor avoids adding a second canvas library for the initial slice and is keyboard operable. It is not an infinite canvas, full graph editor or UI/UX tool. Broader evaluation must cover maintained vector rendering, mobile/keyboard access, import/export security, performance, licensing and accessibility before selecting further dependencies. OCCT and solvers remain subject to the existing CAD gate; none is added here.

## Initial vertical slice
An authenticated, workspace-scoped design dashboard and one structured **conceptual diagram** type, with optional links to an existing product and/or project in the same workspace. Users create editable labeled boxes and directed connections, save structured versioned source, reopen and restore an earlier saved revision as a new revision. All workspace members may read; the creator and workspace owners/admins may edit. Optimistic concurrency rejects stale saves; simultaneous sessions are not real-time collaboration or an exclusive lease. No project task or requirements/test linkage is implied. SVG preview is derived from source, not the authoritative document.

This is deliberately not the whole Stage 1 or Stage 2. Asset uploads/libraries, templates, named versions, comments, sharing, comparison, task/graph links, general-purpose vector editing, UI/UX and AI editors, and CAD are not implemented by this slice. No unsupported create option or control should be exposed. Design history must not be silently overwritten and stale editor content must remain available to copy on conflict.

## Security and data constraints
All reads and writes use the active workspace from authentication; create validates product/project references under that workspace. Revision saves lock the document row, validate source and expected revision, and atomically append a revision before advancing the head. Each document and revision is bounded; diagram labels are rendered as text rather than HTML. No image uploads or untrusted executable code. Demo access is unavailable until explicitly supported. A draft in an unsaved tab can still be lost before autosave completes. Deployed migration version and production backup remain unverified; migrations are not run against production by this work.

## Migration, verification and deployment
Migration `025_design_studio` adds documents and append-only revision tables without backfilling or changing products/projects. It follows the existing pending migrations 023 and 024. The code and schema must be deployed together. Its down migration drops all design data and is **not** a lossless rollback; obtain and verify an appropriate backup and approved recovery procedure before deployment. Production migration state and backup coverage are unknown.

Isolated tests performed: schema/unit validation; a fresh local PostgreSQL instance through migration 025; API creation, product/project workspace checks, cross-workspace denial, creator/admin permissions, concurrent stale-save conflict, revision restoration; structured source reopening after API process restart; and Chromium interaction for create, drag, edit, connect, save, reload, conflict with retained unsaved changes and restore. The browser test used a disposable database/API, not production. Design history stores complete bounded source snapshots; restoring creates a new revision rather than deleting history.

Full roadmap acceptance tests A–F do **not** pass with this slice: no multi-screen prototype, record-linked components/requirements, image/asset graphics, comments, AI-generated drafts or CAD are implemented. The diagram editor now supports SVG and PNG export only. No real-time collaboration, automatic local crash recovery, archive, search beyond the 200 most recently updated documents, named versions, or per-document sharing is provided. Browser/tab crashes or expired sessions may lose work that has not yet reached the server. A revision-based optimistic conflict is not an exclusive single-writer lease. The current confirmation guard covers navigation, workspace switch and sign-out, but cannot guarantee recovery from every interruption.

## Conceptual editor improvements

The existing diagram editor now has a responsive three-column layout on wide screens, a box navigation list, local undo/redo (up to 50 steps, with a drag treated as one step), zoom, a visible grid with optional snap while dragging, box duplication, and SVG/PNG export. Exports represent the current canvas, including unsaved edits, on a white background without the editor grid or selection highlights. Long box labels are truncated in exports just as they are on the canvas. SVG text is escaped and control characters are replaced; PNG is rendered locally in the browser. Zoom uses a scrollable bounded canvas, not infinite canvas or a dedicated pan tool. Undo history is local to the tab and is cleared on restore; it is not durable revision history. Saves retain the existing server-side optimistic revision checks.

These are improvements to the existing boxes-and-connectors document, not a general 2D drawing or 3D product modelling system. Images, freehand drawing, editable shapes/text objects, layers, artboards, project-level access controls and the other requested phase features remain unimplemented. No schema or database migration is introduced. The browser smoke test uses a local mocked API, not a production deployment or a database; existing server-side revision/authorization behavior is unchanged.

## Autosave for conceptual diagrams

Valid diagram changes are saved after two seconds of inactivity, as a new revision using the existing optimistic concurrency check. A user can also save immediately with an optional revision summary. Editing is temporarily disabled while a save is in flight, and navigation, workspace switching and sign-out are blocked until it completes. Invalid labels or coordinates prevent saving and the editor explains what needs correction.

If a save fails, autosave pauses rather than retrying blindly. The unsaved draft stays in the tab, and a JSON recovery copy can be downloaded; importing that copy is not implemented. A lost response may mean the server committed the revision, so users should check the latest revision before retrying or reloading. Stale revision checks prevent an explicit retry from overwriting a newer version. A manual save can resume autosave after a recoverable failure, and a successful restore clears the paused state. Leaving before the debounce completes, browser termination, expired sessions and storage/network failures can still lose unsaved changes; this is not durable local recovery or live collaboration. Autosave can create multiple revisions during a long editing session; the history view remains limited to the latest 200 revisions.

The browser smoke uses a local mock API and exercises validation, delayed saves, navigation/session guards, a committed-but-lost response, no automatic retry and recovery download. A separate browser integration test against a disposable local PostgreSQL 18 and real API verified autosave persistence, reload and concurrent revision conflict; the existing design API permission and revision smoke also passed. These tests do not establish production persistence or backup coverage. No schema change or migration is introduced.
