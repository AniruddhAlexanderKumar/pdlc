# Native CAD Part 1 — independent foundation

## Audit and boundary
The current Design Studio persists conceptual diagrams, not engineering sketches. Its diagram shapes are not CAD entities. There is no CAD editor or production geometry kernel. An experimental, disabled-by-default structured-document API is described below. Existing project/workspace permissions must be reused only after a separately validated sketch document format and API are designed. The current design and migration work, marketing/education changes and earlier OCCT research remain untouched.

The new `@sv/cad-core` package is independent TypeScript with no geometry, solver, CAD, rendering or hosted-service dependencies. The prior OCCT licensing gate remains applicable to the historical OCCT proposal; this native approach does not incorporate OCCT or constitute a legal approval of any third-party CAD distribution. No 3D or Part 2 subsystem is implemented or exposed.

## Units and numerical policy
Core coordinates and dimensions are metres; millimetre conversion is explicit. Numbers must be finite and within documented bounds. Computation uses IEEE-754 binary64, not exact arithmetic. Tolerances and conditioning must be documented per algorithm; never infer a successful solve from an attractive rendering. Sketch source must ultimately be validated before saving, and persisted source—not SVG, solver status or a mesh—is authoritative.

## Status
Part 1 is **not complete** until its interactive editor, authenticated persistence, undo/redo, autosave, recovery, all required primitives/constraints, genuine diagnostics and full acceptance tests exist. No incomplete CAD controls will be shown in the product. Scope excludes B-rep, extrusion and all other Part 2 operations.

## Implemented experimental code (not product-integrated)

- `packages/cad-core/src/math.ts`: native 2D/3D vectors, row-major matrix multiplication, 2×2–4×4 determinant/inverse and 2D/3D transforms. Coordinates are bounded to ±1,000,000 m. Geometry at or below 1e-10 m is degenerate. Millimetre conversions are explicit.
- `geometry.ts`: typed point, line, circle, arc, ellipse, polyline and cubic Bézier records; basic line intersection, circle, arc and cubic Bézier calculations. The spline representation is one cubic Bézier segment with exactly four control points—not a NURBS or general B-spline. These records are not all supported by the solver.
- `sketch.ts`: schema-versioned XY/metre sketch records and basic validation. The experimental sketch/solver supports points, lines, circles and arcs only. IDs and metadata are supplied by the caller; this is not an authenticated document boundary. Constraints currently share one typed array rather than the requested separately modeled geometric and dimensional collections.
- `solver.ts`: builds dimensionless residual equations, approximates a Jacobian by central differences, uses a damped least-squares iteration with column-pivoted modified Gram–Schmidt QR, and estimates local Jacobian rank using pivoted elimination. DOF is unknown-variable count minus the estimated rank, not a count of constraints. It supports coincident, horizontal/vertical, parallel/perpendicular, equal length, fixed point/line, horizontal/vertical/linear distances, line length, radius/diameter and directed angle. Edits are attempted on a candidate and failed/uncertain attempts return the original sketch unmodified.
- `core.test.ts`: isolated numerical and structured-source tests. `scripts/benchmark.ts`: a repeatable narrow microbenchmark.

### Numerical limitations and safety boundaries

This is experimental and must not be used as a production CAD solver. A local numerical rank is not a global proof of constraint independence or uniqueness. Pivot thresholds, finite differences, poor scaling, non-linear local minima and ambiguous branches can produce inaccurate diagnoses; no claim of general robustness or completeness follows from the rectangle test. Angle uses the signed oriented angle from the first directed line to the second in [-π, π]. Horizontal/vertical distances are signed; line and ordinary point distance are unsigned. Parallel permits either direction. Redundancy reports dependent *equations* at the solution, not the particular constraint responsible; a redundant sketch can still have remaining DOF.

The solver reports explicit inconsistency only for a small set of directly matching conflicting dimensional/fixed-point targets; other nonconvergence and obvious singular/threshold cases are `uncertain`, not a fabricated conflict. It does not produce a minimal conflict set. Candidate solutions violating the source validation or bounds are rejected. The residual convergence bound is at most 1e-9 in dimensionless coordinates and at most 1e-9 m for normalized length equations; angular equations are dimensionless. This mixed bound and the finite-difference/rank thresholds need independent calibration. Input is limited to 64 scalar variables and 128 equations for solving; features smaller than 1e-5 of the normalized sketch scale are rejected as uncertain. These are conservative implementation limits, not validated engineering tolerances. `maxResidual` is dimensionless, not a uniformly metre-valued error. Fixed circle/other geometry, arc endpoint constraints, ellipse/polyline/spline constraint support, robust branch management and comprehensive singularity/ill-conditioning detection remain unfinished. Arc radius and center constraints are supported; its start and sweep remain free variables.

Do not treat the core TypeScript validator itself as a hardened network schema. The separate experimental server schema and workspace authorization described below enforce the HTTP boundary. The original core JSON round-trip tests remain in-memory tests, not browser recovery tests. No CAD controls are exposed in the product.

## Verification as of 2026-11-05

- `npm run typecheck`, `npm test` (68 tests, including 10 native-core tests) and `npm run build` passed across the workspace. `git diff --check` passed for tracked changes. Build retained existing chunk-size and Tailwind sourcemap warnings.
- The native tests exercise a four-line 10×20 mm rectangle, rank 16 and zero DOF, width edit to 12 mm, an in-memory JSON round-trip followed by height edit, as well as selected underconstraint, redundancy, direct conflict, geometric constraint, degeneracy, large translation and resource-limit cases. This is **not** the UI/save/reopen acceptance test and does not prove a general solver.
- Run `node --import tsx packages/cad-core/scripts/benchmark.ts`: in one Linux x64 sandbox run with Node v22.22.3 on an Intel Xeon 2.60 GHz, 10 warmups and 100 identical 16-variable/16-equation rectangle solves gave p50 0.801 ms, p95 3.122 ms and max 6.187 ms. This is an uncontrolled, single-process microbenchmark, not a latency guarantee or large-sketch benchmark.
- At that earlier checkpoint there was no CAD API or persistence integration. See the later continuation evidence below. No third-party CAD/geometry/solver/rendering package was added; TypeScript, Node types and `tsx` are development infrastructure only.

## Part 1 continuation — 2026-11-05 (still incomplete)

### Implemented locally

- Additive migration `026_native_sketch_documents.ts` adds workspace-owned `cad_documents` and append-only `cad_document_revisions`. Rows contain structured editable sketch source, not SVG or screenshots. List/create/read/save/rename/archive/unarchive are implemented at `/api/cad-documents` in `routes/cad-documents.ts`. Workspace members can read; only the document creator or workspace owner/admin can edit/archive. Archived documents can be listed and restored within the same authorization policy. Both save and archival changes use locked rows and expected revisions; competing saves cannot silently overwrite one another.
- The API is **disabled by default** (`CAD_NATIVE_EXPERIMENTAL=false`) and has no product UI. Explicitly opting in is for controlled local development only, not an indication of production readiness. Normal boot still registers and applies migration 026 even with the API disabled: deployment needs prior authorization, migration/backup review and production verification. `down` drops both CAD tables **and all their documents and revisions**. Do not use it as a routine rollback; disabling the API leaves data intact. The migration was applied only to a disposable local fixture, not production.
- Strict Zod network validation in `services/cad-validation.ts` rejects unknown fields, unsupported versions/types, invalid references, duplicate IDs and invalid geometry. The server authoritatively assigns/preserves entity owner and creation metadata, solves candidates and rejects inconsistent or uncertain solutions. Reopen validates and reconstructs the solver from stored source, without persisting a display object or trusting a submitted status. The server's experimental limits are 32 scalar variables and 64 equations, stricter than the core's limits. Synchronous solving still needs performance and denial-of-service review before production exposure.
- `packages/cad-core/src/document.ts` defines the wire document contract. `editor.ts` supplies unintegrated pure sketch history transactions, rectangle construction from four lines with eight connectivity/orientation constraints, removal of attached constraints, geometry movement and point/grid snapping. Undo/redo snapshots preserve geometry and constraints, but are not connected to a browser editor and are not yet integrated with server revision advancement. Failed numerical transactions retain the prior history. Arc records now have center/radius/start/sweep solver variables; center/radius constraints are supported, but arc endpoints and orientation cannot yet be constrained or snapped.
- The source encodes `plane: 'XY'` and `units: 'm'`; an explicit serialized coordinate-frame contract and separate persisted geometric/dimensional constraint collections remain to be designed. The experimental solver is unchanged in its numerical algorithm; the arc support extends its variable packing. Constraint semantics and numerical limitations above still apply.
