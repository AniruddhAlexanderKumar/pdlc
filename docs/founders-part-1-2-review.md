## Logging and telemetry evidence

PostgreSQL 17.9 was run locally with the checked-in Compose logging options. The separate constraint regression reproduced SQLSTATE 23514 and confirmed the synthetic failing-row hash existed in the driver DETAIL but not in the captured PostgreSQL or sanitized app log or HTTP response. That regression manually sets PostgreSQL `application_name` to its correlation ID; real founder transactions do not yet propagate it.

A separate local subprocess ran the **actual experimental app logger** in development mode and captured app and CLI output. It exercised invalid login, MFA failure, invalid session, an unknown/recovery path, a synthetic bootstrap failure, and induced database failures on login and session lookup. No unique synthetic input appeared in captured logs or error responses; the intentionally returned enrollment secret was absent from logs. Structured request events contained time, server-generated ID, allowlisted method/route, status and duration; a DB error included safe SQLSTATE 42P01 and correlation ID. The recovery path only proved 404, not an implemented recovery failure. The test did **not** capture PostgreSQL logs for every one of these operations; the separate PG sentinel test covers the constraint. It did not inspect browser diagnostics, network capture, reverse proxies, background jobs, real CI output, error reporting, tracing or monitoring. No configured external error-reporting/tracing integration was found in the inspected server sources, but platform collectors and deployment overrides are unknown. Caddy and nginx config files exist; neither proxy was running in this rehearsal. `log_min_error_statement=error` can expose literal SQL and TERSE does not remove arbitrary MESSAGE text or third-party instrumentation. These limitations preclude an end-to-end redaction claim.

## Rate limits and remaining lockout abuse

The experimental router uses a 15-minute fixed window with per-action IP budget 30 and account/IP budget 8. The local CLI uses budget 4. After the free budget, cooldown starts at 5 seconds, doubles on later attempts up to 300 seconds and does not extend during an active bucket cooldown. Keys are HMACs over scoped identifiers; a separately protected 32-byte key is required. DB failure fails closed. Local cleanup deletes at most 1,000 rows per run only after both timestamps exceed two days and no block remains; in the experiment it runs during the existing 15-minute sweep. A compromised key or rotation resets effective buckets. Shared NAT, proxy topology, IPv6 grouping and distributed sources require real ingress tests. Local retention and request logs are not monitoring or alerts.

The older account-wide five-failure/15-minute lock remains. This work stops an already locked account's later unauthenticated attempts from extending that same deadline or increasing the failure counter, but after expiry an attacker can trigger the next lock again and can cause repeated disruption. A correct password is currently rejected while locked. This is **not** acceptable closure of lockout-abuse prevention. Do not expose this experiment in production until an independently reviewed policy addresses distributed password and six-digit MFA guessing, abusive account targeting, shared IPs and legitimate recovery without an easily triggered account-wide denial of service.

## Audit role model and limits

The prototype provisioning function is never called from HTTP or startup. It accepts four distinct pre-created roles: no-login audit-table owner, no-login insert-only writer, no-login read-only audit reader, and app login. The app inherits writer; writer can insert only event type, typed actor/role/target/outcome and generated request ID, while DB defaults create ID/time. Reader can SELECT but not write. The primitive refuses known elevated/owner/schema-create memberships, unexpected grants and dangerous effective or SET ROLE-reachable audit privileges; changes are transactional. It is a **prototype**, not an approved provisioning command: it is not wired into deployment and deliberately refuses existing column ACLs rather than attempting an unsafe in-place reconciliation. Operators must inspect role membership, schema/DB ownership, default grants, other schemas/functions, writer access and actual privileges independently. Normal application tables require separately reviewed operational grants; the test's broad fixture-only operational table grants are not a production policy.

The test used real separate PostgreSQL logins, not only `SET ROLE` from a superuser. It proved the model's local restrictions and transactional failure handling. The table owner, DB owner, superuser, a compromised provisioning operator or any alternate privileged logging destination can still alter/fabricate events. An app writer can fabricate allowlisted events, so independently controlled retention, reconciliation and alerts remain required. No real staging identities were provided or tested.

## Recovery and bootstrap operational design — not an executable procedure

**Password recovery:** require generic responses independent of account existence and Owner exclusion; high-entropy tokens must remain hashes in DB, expire after 20 minutes, be one-time and invalidate prior tokens. Deliver only to a verified contact through configured non-production SMTP; a delivery failure must invalidate the token safely. The recovery page must clear the URL fragment, avoid third-party scripts/referrer leakage, validate a new password and revoke sessions and flows atomically while retaining MFA. Rate-limit both request and completion without creating an easy account lockout; audit outcomes without tokens. The current code has no endpoint or page, so this design has not been implemented or verified.

**Owner break-glass proposal:** an authorized security operator initiates a documented incident when authenticator/recovery codes are lost, compromise is suspected, a session is suspicious, or the Owner is suspended. Independently verify identity using pre-enrolled out-of-band contact and previously established evidence—not an incoming email, unauthenticated request or a claimed identity. A separate authorized approver validates the incident, scope, expiry and identity through an independent channel. For multiple Owners, use at least two separate eligible approvers; for a sole Owner, provision at least two independent restricted operational custodians in advance. Neither ordinary Admin nor Operations may approve alone or reset Owner via HTTP. Grant a short-lived, single-use, scope-bound action only after approval; atomically invalidate old sessions, flows, factor material and recovery codes, return the Owner to pending MFA enrollment, require password rotation, persist audit and independently notify the Owner/security contact. Record incident ID, authorized actors, outcome and time without secrets; separately alert and reconcile. A suspended account must remain suspended until independently authorized reactivation; an MFA reset must not silently unsuspend it. Revoke the temporary grant on success, expiry or cancellation, and rehearse compromise and interrupted execution. This is a design, not a working tool: custodians, identity verification, separate approval keys, safe database authority, notification path and implementation are missing.

**Bootstrap proposal:** a separately authenticated, explicitly authorized operator starts a one-time action. An independent approver and protected authority provision a short-lived, scope-bound authorization for the fixed Owner identity; verifier material must not be controlled by the operator or supplied as an overrideable environment digest. Deliver the initial password separately through the approved secret manager, not command arguments, logs or documents. Under a locked singleton transaction verify the approved authorization and identity, reject ordinary-user collisions, create the pending account, commit audit and consume the authorization atomically. Require MFA enrollment and first-login password rotation, invalidate credentials and prevent reuse, and resolve uncertain outcomes by checking state without revealing secrets. Validate signer/authority, expiry, action, intended database, operator, replay and concurrency independently. Existing CLI is a local experiment and does **not** implement this independent authority; production remains refused.

## Migration 027/028 and controlled release runbook

027 adds isolated accounts, bootstrap state and audit plus mutation triggers; 028 adds encrypted TOTP metadata and authentication-flow, session, recovery-code and password-recovery tables/indexes. Both security down functions refuse destructive rollback. 028's `ALTER TABLE` and validation take strong locks, and existing active founders without required ciphertext can prevent migration. 029 and 030 add limiter and audit validation; all are currently statically registered for startup. Kysely's PostgreSQL adapter acquires a session advisory lock with a one-hour timeout and applies the pending batch in a transaction. Startup logs now avoid reporting earlier batch steps as committed if a later migration fails. First-time concurrent migrator metadata initialization may log duplicate-object errors even when Kysely recovers. A real backend termination was tested locally; the fault-injection harness needed a per-client socket-error listener, so application behavior during equivalent network failure still needs separate review.

1. **Do not execute now.** Obtain explicit release approval; inventory actual DB/version, runtime and migration identities, complete migration history, schema drift and pending unrelated migrations; determine deployment/restart/rollback strategy and confirm founder production boundaries stay closed.
2. Take an encrypted backup and verify restore into a completely isolated environment. Establish RPO/RTO, actual backup permissions and safe retention; use representative sanitized data and production-equivalent roles. No backup/restore has been verified in this session.
3. Review migrations 027–030 and all earlier pending migrations, strong-lock durations, startup rollout compatibility and security grants. Separately provision the migration identity and unprivileged runtime identity after independent review; verify runtime cannot own or mutate the audit table and has read-only `SELECT` on `public.kysely_migration`.
4. Rehearse the dedicated migration job and ordinary auth on the restored isolated copy. The repository's `npm run migrate --workspace @sv/server` applies **all** pending migrations, not only founders. Under an approved controlled deployment, `MIGRATIONS_ON_STARTUP=false` prevents startup DDL and requires the exact migration history in this build. Missing, extra or differently named records prevent startup; older application builds will refuse a newer history during a rolling rollout. This check compares migration names, not schema contents or checksums. Legacy startup remains automatic by default. Do not enable the new mode without a rollout plan, separately authorized job and permissions.
5. During an approved maintenance window, run the migration job once under the authorized migration role. Hold application rollout/restart loops as needed; monitor locks, storage and sanitized SQLSTATEs. Verify migration records, constraints, indexes, triggers, grants, audit export, account state, app health and normal authentication. Never output credentials or sensitive rows.
6. On failure, stop retries, inspect committed state and transaction outcome and use a reviewed forward fix or an authorized restore. Security down functions deliberately refuse deletion and migration 026 down destroys CAD data; do not run them. Recheck runtime role, startup guard, backups and monitoring before resuming. No production migration, restore or deployment was authorized here.
