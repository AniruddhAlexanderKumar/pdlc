# Teamwork Graph: implemented scope

The graph is a workspace-scoped projection of existing records: workspace membership, projects and issues, plus the separate PDLC products and checklist tasks. Project/issue containment, product/task containment and issue assignment come directly from their source tables. Projects and products are distinct in the current model: the graph does not infer links between them. The original application has no first-class requirements, design documents, verification, evidence, release, team, issue comment or activity-history models, so these are not fabricated in the graph.

Workspace members can create directional `depends_on` and `relates_to` links between issues, consistent with existing issue-edit permissions. Source and target must be in the active workspace; self-links, duplicates, unsupported types and dependency cycles are rejected. Relationship creation, description edits and deletion are transactionally audited. A workspace-scoped advisory lock prevents simultaneous dependency inserts from creating cycles. Existing membership, assignment and containment edges are derived and cannot be edited as graph links. Impact follows recorded dependency edges in reverse; it does not claim engineering consequences. The issue-link picker can search for targets outside the currently loaded canvas.

The initial graph is bounded to 200 records of each kind and 2,000 explicit links, with a warning when results are truncated. Project selection scopes issues to that project and suppresses products/tasks. Cross-project edges appear in the all-project view when both endpoints are loaded, or in a focused issue view. Workspace search queries the database independently of the initial canvas and returns up to 20 results of each kind. Selecting an issue loads up to two levels of its explicit issue relationships, including cross-project relationships, with at most 200 issues. The canvas filters, impact view and JSON export apply only to currently loaded nodes; focused views and search results may be truncated. The graph polls every 15 seconds and on window focus; it is not a subscription or real-time event stream. Layout positions are local to the open view. Collaboration counts describe loaded records, not the complete workspace. This is not yet suitable for complete analysis of large workspaces.

## Assistant

The configured AI model is used only to classify a user's question into a fixed list of operations. No database records are sent to the model. The model cannot supply SQL, create relationships, or supply result records. The server executes workspace-scoped queries and returns up to 50 real issues, with links to supporting records for dependency, impact and duplicate findings. Duplicate suggestions are based on exact normalized summaries and require human review; they do not create a relationship. Supported queries cover recorded issue links, downstream dependents, unassigned work, unresolved high-priority issues, blockers, issues without explicit issue links, exact-summary duplicate candidates and assignments to a uniquely named workspace member. The configured AI endpoint must be available; invalid model output or an unavailable service returns an error rather than invented results. The question text is sent to the configured AI endpoint, so operators must configure an appropriate trusted service. The model can misclassify a question; the UI states the interpreted operation and all results should be reviewed.

## Remaining gaps

Engineering traceability for missing record types, project-wide pagination and complete neighborhood traversal, subscriptions, full collaboration analytics, AI-proposed relationship creation, comment/activity feeds, undo/redo, share links, and a full mobile/end-to-end browser test suite remain unimplemented. These require further product, data-model and validation work before the feature meets the complete requested acceptance criteria. Search, focus and AI results are bounded; they are not evidence that no other records or consequences exist.

## Verification

- `npm run typecheck`, `npm test`, `npm run build`, `npm audit --omit=dev`
- To run the integration smoke test against a **disposable** database/server only: `GRAPH_SMOKE_URL=http://localhost:4000 node apps/server/scripts/teamwork-graph-smoke.mjs`. It creates test accounts and workspaces. Set `GRAPH_SMOKE_LARGE=1` to create over 200 issues and test search/focus outside the initial page.
- To additionally test the assistant without a real model, run `node apps/server/scripts/graph-ai-stub.mjs`, configure the test API with `AI_BASE_URL=http://127.0.0.1:8097/v1`, and run the smoke test with `GRAPH_SMOKE_AI=1`. The stub is test-only and must never be exposed in production.
- Migrations `007_teamwork_graph` and `008_graph_search_indexes` are registered with the existing migrator and run on server startup; these tests do not modify a production database.
